# SM100 vs SM120

数据中心版 Blackwell（计算能力 10.0，即 CC 10.0）与工作站/消费级 Blackwell（计算能力 12.0）之间的架构差异。这是本 wiki 最重要的一页。

## 代号

| 计算能力 | NVIDIA 代号 | 产品 | 形态 |
| --- | --- | --- | --- |
| 10.0（SM100） | GB100、GB200、GB300 | B100、B200、B300；GB200/GB300 超级芯片 | SXM、PCIe |
| 12.0（SM120） | GB202 | RTX PRO 6000 Blackwell **Server Edition**、RTX PRO 6000 Blackwell **Workstation Edition**、RTX 5090、RTX 5080 | PCIe |

关于“RTX PRO 6000 Blackwell”这个品牌要说明一下：Server Edition 和 Workstation Edition **都是** GB202 / SM120——和 RTX 5090 是同一块硅片，只是散热和供电形态不同。它们**不是**数据中心版 Blackwell。SM100 只给 B100/B200/B300 这些 SXM 产品和 GB200/GB300 超级芯片。只要你的卡名字里带“RTX PRO 6000”，你用的就是 SM120。

## 相同的部分

- **Tensor Core 世代**完全一样：第 5 代，原生支持 FP4/FP6/FP8/BF16/FP16
- **PTX ISA 主版本**：8（截至 2026 年次版本为 5）
- **驱动与 CUDA 工具包**：同一套二进制两边通用
- **线程模型**：32 线程的 warp、CTA/block、grid 层级
- **L1/L2 缓存架构**：概念结构相同（容量不同）
- **原生 NVFP4 + MX-FP4 GEMM**：两边都有

## 不同的部分

### 1. `tcgen05` 指令族

**SM100 有，SM120 没有。**

随数据中心版 Blackwell 引入的一族新 PTX 指令：

- `tcgen05.alloc` / `tcgen05.dealloc` —— 管理 Tensor Memory 的分配
- `tcgen05.mma.cta_group::1` / `cta_group::2` —— 发射大 tile 的异步 MMA，结果写入 TMEM
- `tcgen05.commit` —— 把已发射的异步 MMA 挂到一个 mbarrier 上，完成时通知
- `tcgen05.ld` / `tcgen05.st` —— 在 TMEM 和寄存器之间搬数据
- `tcgen05.cp` —— 从 SMEM 拷贝到 TMEM（只有这一个方向；译注：原文写"以及反向"，ISA 里没有）
- `tcgen05.shift` —— 把 TMEM 里的数据下移 32 个 lane（配合 weight-stationary MMA 用）

只要 PTX 里含有其中任何一条，用 `--gpu-name=sm_120` 汇编时 `ptxas` 就会报“instruction not supported”。没有回退路径，kernel 必须重写。见 [`tcgen05-and-tmem`](tcgen05-and-tmem.md)。

### 2. Tensor Memory（TMEM）

**SM100 每个 SM 有 256 KB，SM120 没有。**

一种新的片上存储，独立于寄存器和 SMEM，专门存放 Tensor Core 的累加器。见 [`fundamentals/memory-hierarchy`](../fundamentals/memory-hierarchy.md) 和 [`tcgen05-and-tmem`](tcgen05-and-tmem.md)。

没有 TMEM，累加器只能放在下面两处之一：

- **寄存器**：每线程最多 255 个 32 位寄存器。一个 128×128 的 FP32 累加器（64 KB）在一个 warp 的寄存器里放不下（一个 warp 满打满算也只有 32 KB）。
- **SMEM**：SM120 上每 block 最多 99 KiB，还要和操作数暂存缓冲区、流水线状态共用。

所以 SM120 上的 GEMM 必须用**比 SM100 更小的累加器 tile**。

### 3. 每 block 共享内存上限

**SM100：每 block 228 KiB。SM120：每 block 99 KiB。**

这是移植 kernel 时影响最大的一个架构参数。CUTLASS 模板、FlashAttention 流水线和很多自定义 kernel 都是按可用 SMEM 的大小来决定流水线各级缓冲区大小的。为 SM100 编译的模板用 `StageCountAutoCarveout` 可以申请到约 220 KiB，并默认启动一定成功。

同一个模板在 SM120 上不会静默跑坏：用 `cudaFuncSetAttribute` 申请超过 99 KiB 的动态共享内存会返回 `cudaErrorInvalidValue`，直接按超额大小启动也会报启动失败。**麻烦在于这个错误直到运行时才出现**——为 SM100 编好的模板要真正启动时才暴露，而且很多上层库会把这个错误吞掉、换成一句含糊的"kernel 不可用"（译注：原文称"申请被悄悄截断、写越界、没有任何错误码"，与 CUDA 实际行为不符，已改）。

CUTLASS 里对应的经典 issue 是 `NVIDIA/cutlass#3096`，它跟踪的就是为了在编译期发现这个问题而需要做的 SM120 审查。

### 4. 线程块簇

**SM100 支持最多 16 个 CTA 的 cluster。SM120 只支持 cluster 大小为 1（也就是没有 cluster）。**

*cluster*（Hopper 引入，数据中心版 Blackwell 扩展）是一组 CTA，它们：

- 跨同一组相邻 SM 的 SMEM 共享一个*簇共享内存*地址空间
- 可以用 `cluster.sync` 同步
- 可以发射 cluster 范围的 TMA（`cp.async.bulk.tensor.shared::cluster.global`）

声明了 `.cluster_dim 2,1,1` 的 kernel 需要 SM100 才能真的以 2 个协作 CTA 运行。在 SM120 上，cluster 维度被悄悄降成 `1,1,1`——kernel 照常启动，但它期待的搭档 CTA 并不存在。任何和搭档同步的操作要么死锁，要么算出错误结果。

见 [`thread-block-clusters`](thread-block-clusters.md)。

### 5. TMA——Tensor Memory Accelerator

**SM100 同时有单 CTA 和 cluster 共享两种 TMA。SM120 只有单 CTA TMA。**

TMA 是硬件 DMA 引擎（Hopper 引入），在全局内存和 SMEM 之间异步拷贝张量 tile，自带多维 tile 的寻址逻辑。单 CTA TMA 在 Blackwell 两个分支上都有（Hopper 也有）。cluster 共享 TMA 可以把一个 tile 一次性铺到多个 SM 的 SMEM 里，只有 SM100 才有。

### 6. NVLink 与 MNNVL

**SM100 级别的卡通常有 NVLink，SM120 级别的卡没有。**

这属于产品分级，严格说不是 SM 特性，但实际上两者完全对应：NVIDIA 不在消费级 Blackwell SKU 上提供 NVLink 桥接或 NVLink 端点。影响在 [`interconnect/`](../interconnect/index.md) 中讨论。

### 7. 显存与带宽

| | SM100（以 B100 为例） | SM120（以 RTX PRO 6000 W. 为例） |
| --- | --- | --- |
| 显存类型 | HBM3e | GDDR7 |
| 容量 | 192 GB | 96 GB |
| 带宽 | 8 TB/s | ~1.8 TB/s |
| L2 缓存 | ~50 MB | ~16 MB |

这是硬件成本问题，不是 ISA 问题。哪怕软件做到完美，SM120 卡的显存带宽就是更低——对访存受限的负载（长上下文 decode、极小 batch）影响明显。

### 8. PCIe 代际

| | SM100（PCIe 版本） | SM120（消费级卡） |
| --- | --- | --- |
| PCIe | Gen5 x16（典型） | Gen5 x16（消费级/工作站），旧平台上为 Gen4 |

原则上一样；实际上消费卡往往插在工作站主板上，可能只能跑 Gen4（每方向 32 GB/s）或不太稳的 Gen5。

### 9. P2P 特性

**SM100 数据中心产品通常支持经 NVLink + MNNVL 的 P2P。SM120 支持 PCIe P2P，但原子操作受软件限制。**

细节见 [`interconnect/p2p-and-atomics`](../interconnect/p2p-and-atomics.md)。

## 故障模式小结

把 SM100 软件跑在 SM120 上，上面这些架构差异会分别表现为下面这些具体的故障：

| 软件依赖…… | SM120 上的表现 |
| --- | --- |
| `tcgen05.*` 指令 | `ptxas` 报“instruction not supported”；若是预编译的，则运行时报“no kernel image” |
| TMEM 分配 | 同上 |
| cluster 大小 > 1 | 悄悄降成 cluster 1；随后的 `cluster.sync` 死锁 |
| cluster 共享 TMA | TMA 描述符校验时运行时报错 |
| 228 KiB SMEM 上限 | 启动成功；SMEM 分配越过 99 KiB 边界，输出被悄悄写坏 |
| NVLink 级别的带宽 | 操作能完成，但只有 PCIe 的速度（all-to-all 流量常慢 30–50 倍） |
| P2P 原子操作 | 原子操作返回“not supported”；忙等循环永远等不到完成；看门狗超时 |

前四种是**显式故障**——你会拿到报错或者卡死，知道出了问题。后三种是**静默或性能故障**——程序跑完了，但结果是错的，或者慢得像爬。静默这一类更危险。

## 能怎么办

三类办法，在 [`compatibility/`](../compatibility/index.md) 中展开：

1. **替换**——把只支持 SM100 的 kernel 换成另一个库里面向 SM120 的等价 kernel
2. **降级改写**——把 SM100 的 PTX 重写成 SM120 的 PTX，用一串 `mma.sync` 替代 `tcgen05`，用更小的寄存器/SMEM 累加器替代 TMEM
3. **重新规划**——在模型系统层面改并行方案（EP → TP+PP），让依赖 SM100 的代码路径根本不被走到

每一类都有取舍。怎么选取决于你的性能预算和你真正需要什么。
